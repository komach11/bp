# 密室 → 海岛捕鱼 场景衔接说明

本文说明两个场景如何串起来，以及**还剩什么没做**。

---

## 一、当前完成度

| 步骤 | 状态 |
|---|---|
| 1 · 道具池收窄到捕鱼可用的 4 种 | ✅ 已完成 |
| 2 · 结算界面只展示携带清单 | ✅ 已完成 |
| 4 · 场景跳转与数据交接 | ✅ 已完成（单机可跑通） |
| 3 · 密室联网化 | ❌ **未做**，见第五节 |

**现在可以验证的闭环**：密室搜到大渔网 → 结算界面显示"红方：大渔网" → 跳到捕鱼场景 → 手里真的有大渔网。

**注意**：这个闭环在**单机 / 主机自己玩**的情形下成立。多人联机时其他客户端拿不到数据，因为密室本身还不是联网的。

---

## 二、道具收窄（第 1 步）

`RoomConfig` 新增两个字段：

```
restrictToCarryableItems = true      只掉落能带进下一关的道具
carryableItemIds = [net_large, net_small, knife, mine]
```

开着时，搜索容器只产出这 4 种。做饭（辣椒、平底锅…）与警察（手铐、警犬…）主题的道具**仍在池子里但不会掉出来** —— 保留给后续场景，不用删数据。

做后续场景时把 `restrictToCarryableItems` 关掉，或往 `carryableItemIds` 里加对应 id。

### 顺带修的一个 bug

`GetPool()` 原先在找不到指定主题时会**无条件退回任意非空池**，导致设了 Fishing 主题却可能掉出做饭道具。现已改为只在完全找不到时才退回。

---

## 三、结算界面（第 2 步）

按要求改为**只展示各玩家获得了什么，不折算分数、不排名**：

```
        搜刮结束 · 携带清单
     这些道具将带入下一环节使用

  红方       大渔网　小刀
  蓝方(AI)   小渔网
  黄方(AI)   空手离场
  绿方(AI)   水雷　大渔网

      即将进入：GameScene_PartyFishing
```

- 按固定队伍顺序排列（红蓝黄绿），不按成绩
- 下一关用不了的道具会标 `(仅收藏)`，避免玩家误会
- 停留时长由 `RoomManager.settlementDisplayTime` 控制，默认 4 秒

## 四、数据交接（第 4 步）

### 密室侧

`CarryOverData`（已从 `RoomManager.cs` 独立成 `Scripts/Core/CarryOverData.cs`）：

```csharp
CarriedLoadout {
    int slotIndex;          // ★大厅槽位 0~3，两场景唯一可靠的身份纽带
    bool isBot;             // 密室 AIBrain → 捕鱼 PartyPlayerAI
    PlayerColor color;      // 仅结算界面显示用
    List<string> itemIds;   // 道具 id
    List<string> itemNames; // 中文名，仅显示用
}
```

**为什么按 slotIndex 而不是 PlayerColor**：捕鱼场景的 `LanLobbyManager` 用 `slotIndex` 标识玩家，`PlayerColor` 是密室内部概念，对面不认识。`PlayerColor` 的 0~3 正好对应槽位 0~3。

**为什么只传 string id**：两个场景的道具资产是各自独立的（密室 `ItemDefinition` vs 捕鱼 `ItemDataSO`），不能传对象引用。

### 捕鱼侧

接收端代码在 `_Docs/衔接代码_捕鱼侧_CarryOverReceiver.cs.txt`，**需要复制到内网工程** `Assets/Scripts/PartyGame/Net/CarryOverReceiver.cs`。

接入只需改 `PartyPlayerSpawner.SpawnFor()` 末尾一处：

```csharp
// 原本
var mgr = PartyGame.PartyGameManager.Instance;
if (mgr != null && pp != null) mgr.EquipDefaultLoadoutFor(pp);

// 改成
if (!CarryOverReceiver.TryEquipFromCarryOver(pp, slot))
{
    var mgr = PartyGame.PartyGameManager.Instance;
    if (mgr != null && pp != null) mgr.EquipDefaultLoadoutFor(pp);
}
```

有密室数据就用，没有（直接从大厅开局）就发默认装备。

**为什么选这个时机**：道具槽是 `NetworkVariable`，只有服务端能写，且必须在 `PartyPlayer` Spawn 之后。`SpawnFor()` 末尾正好满足两个条件，原作者的注释也说明这里是为了避开 `FindObjectsOfType` 与 spawn 的时序竞争 —— 蹭现成的最稳。

### 场景跳转

`RoomManager.LoadNextScene()` 会自动判断：

- Netcode 正在运行且自己是服务端 → 用 `NetworkSceneManager.LoadScene`（全端同步）
- 否则 → `SceneManager.LoadScene`（单机）

用反射探测 Netcode，所以密室**既能脱离捕鱼工程单独测试，也能作为联网流程的一环**。

## 五、还没做的：密室联网化（第 3 步）

这是剩下的主要工作量。密室现在是彻底的单机架构：

| 现状 | 联网需要改成 |
|---|---|
| `PlayerActor` 是 `MonoBehaviour` + `CharacterController` | `NetworkBehaviour`，移动改服务端权威或客户端预测 |
| `HumanBrain` 直接读 `Input` | 输入经 RPC 上报，或用 owner 权限 |
| `PlayerInventory` 本地 List | `NetworkVariable` 或服务端权威 + 同步 |
| `SearchContainer.remainingYield` 本地 | 服务端权威，否则各端搜到的东西不一样 |
| `FloorTile` 塌陷由本地协程决定 | 服务端决定塌哪块、何时塌并广播，否则有人踩空有人没事 |
| 自己 `StartRound()` | 接入现有 `LanLobbyManager` 流程 |

**建议顺序**：先用现在的单机版把玩法闭环验证舒服了，再做联网。理由是如果发现设计问题（比如只有 4 种道具太单调），改设计比改联网代码便宜得多。

---

## 六、Unity 里要做的配置

1. 打开密室场景，选中 `RoomManager`
2. `nextSceneName` 填 `GameScene_PartyFishing`
3. **`loopForTesting` 取消勾选**（配了下一关时它会打架，代码里已加保护，但配置上也理清更好）
4. `settlementDisplayTime` 按需调整，默认 4 秒
5. 两个场景都要加进 Build Settings 的 Scenes In Build

单独测试密室时把 `nextSceneName` 清空即可，会停在结算界面并按 R 重开。
